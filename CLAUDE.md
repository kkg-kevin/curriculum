# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

**Run everything (dev mode):**
```bash
npm run dev          # from repo root — starts both client and server concurrently
```

**Run individually:**
```bash
cd client && npm run dev   # Vite dev server (default: http://localhost:5173)
cd server && npm run dev   # nodemon (default: http://localhost:5000)
```

**Install dependencies** (run from each directory separately — there is no root-level install script):
```bash
npm install            # root
cd client && npm install
cd server && npm install
```

**Tests (server):**
```bash
cd server && npm test                                  # no database needed
cd server && TEST_DB_NAME=digifunzi_nfr_test npm test   # also the database tests, against a throwaway database (name must end in _test)
```

**Lint / format (client):**
```bash
cd client && npx eslint src
cd client && npx prettier --write src
```

## Architecture

This is a **feature-based monorepo** with no shared code between `client/` and `server/`. Each side mirrors the same domain boundaries (schools, learners, teachers, classes, curriculum, assessments, reports, settings).

### Client (`client/` — React 19 + Vite + MUI)

Entry: `client/src/main.jsx` → wraps `<App>` in `BrowserRouter`.  
Routing: `client/src/routes/AppRoutes.jsx` — all routes nest under `MainLayout` (authenticated shell with Sidebar + Header + Footer + `<Outlet />`). `AuthLayout` is a stub for login/register pages.  
API: a single Axios instance in `client/src/services/api.js` reads `VITE_API_URL` from the client `.env`. All feature-level API files (`modules/<feature>/services/<feature>Api.js`) import from this shared instance.  
State: React Context for auth (`client/src/context/AuthContext.jsx`). Redux Toolkit + TanStack Query are installed but not yet wired up — use Redux for global UI state and React Query for server state as features are built.  
Forms: react-hook-form + Zod resolvers.  
Charts: Recharts. Rich text: TipTap.

**Planned module structure** (not yet scaffolded — stub pages exist only in `AppRoutes.jsx`):
```
client/src/modules/<feature>/
  pages/         # route-level components
  components/    # feature-specific components
  services/      # <feature>Api.js — calls shared axios instance
```

### Server (`server/` — Node/Express, CommonJS)

Entry: `server/src/server.js` — loads `.env`, starts the HTTP server.  
App: `server/src/app.js` — mounts CORS, JSON body parser, Morgan logger. Routes will be registered here.  
Config: `server/src/config/db.js` exports a Knex singleton connection pool (reads `server/knexfile.js`, MySQL via `mysql2`). `server/src/config/env.js` exports env vars incl. `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`.

### Database (MySQL via Knex)

Every `*.model.js` is a thin Knex query-builder wrapper (no ORM) exposing the same `create/findAll/findById/update/delete` + custom-finder shape regardless of module — services/controllers call these and `await` them like any other async function. JSON-shaped fields (nested arrays/objects like `assessments.items[]` or `course-sessions.mainConcepts[]`) are stored as MySQL `JSON` columns; write them through `stringifyJsonFields`/`toJson` from `server/src/shared/utils/model.utils.js` (mysql2 does not auto-serialize a raw JS object/array on insert, but does auto-parse JSON columns back on read). No DB-level `FOREIGN KEY` constraints — referential integrity is enforced at the application layer, same as the old JSON-file era.

Migrations live in `server/src/db/migrations/` (`npm run db:migrate` / `db:migrate:rollback` / `db:migrate:status`, from `server/`). The one-time JSON→MySQL loaders and the `server/data/*.json` files they read from have been removed now that the migration is complete and MySQL is the sole source of truth.

**Planned module structure** (not yet scaffolded):
```
server/src/modules/<feature>/
  <feature>.routes.js
  <feature>.controller.js   # request/response only, no business logic
  <feature>.service.js      # all business logic lives here
  <feature>.model.js        # DB schema
  <feature>.validation.js   # Zod schemas
```

Shared backend utilities live in `server/src/shared/`:
- `middleware/auth.middleware.js` — JWT verification + role/permission checks (stub)
- `middleware/error.middleware.js` — global error handler (stub)
- `utils/` — `helpers.js`, `logger.js`
- `validators/common.validator.js` — Zod schemas shared across modules

### M-Pesa

`server/src/modules/payments/mpesa/`. Money reaches an invoice only through `BillingService.applyPayment` (staff "Record payment" goes through it too); an invoice becoming fully paid runs `billing.paid-hooks.js`, which switches on Home Learning / Tech Club / Bootcamp website sign-ups. Safaricom calls `/api/public/pay-hooks/<MPESA_CALLBACK_TOKEN>/…`. Every payment received is one `mpesa_transactions` row (UNIQUE M-Pesa receipt), so repeated callbacks can't pay twice; ones that match no invoice wait in Billing → M-Pesa. An invoice's Paybill account number is its number without prefix/dashes (`INV-2026-000123` → `2026000123`). Cron: `npm run mpesa:reconcile` every 5 minutes; once per Paybill: `npm run mpesa:register-urls -- --yes`. Plan and status: `Guide/MPESA_INTEGRATION_PLAN.md`.

### Settings → Pathways is a read-only directory

The real pathways live in the curricula (Curriculum → Competency Framework → Pathways, one `pathways` row per developmental stage; same-named rows = one pathway). A pathway's courses come only from its curriculum's version (published or draft — `CurriculumVersionService.versionCourseIds`, client `useVersionCourseIds`): the stage editor's picker offers only those (`CoursePickerField`'s `allowedIds`; older picks outside it stay, marked "not in version"), the pathway create/update routes refuse ADDING any other (`competency.controller.js`'s `assertCoursesOnVersion` — internal flows like duplication aren't checked), and importing a catalogue pathway keeps only its version courses (4 Nov 2026). Settings → Pathways (`PathwayTemplatesPanel`, `GET /api/pathway-templates/directory` → `PathwayTemplateService.getDirectory`) only shows them, worked out fresh on every load: each pathway with the curricula using it, its courses per stage and its learners ("In use"), then catalogue entries no curriculum uses ("Not in use"). Nothing is edited there — "Open in curriculum". The catalogue (`pathway_templates`) stays as what courses and assessments are tagged with; `competency.service.js`'s `syncCatalogue` keeps it in step (a new curriculum pathway gets an entry; a rename carries its entry once no curriculum uses the old name), and migration `20261102140000` backfilled entries for every pathway already in use. **Website:** each in-use pathway has an "On the website" section — in Billing → Packages → Pathway plans since 4 Nov 2026, no longer in Settings — `pathway_templates.websiteVisible` (default true, so nothing vanished on deploy) and `websiteHubIds` (the hubs it runs at; workspace active hubs only, never the Home Learning holder) and `websiteImage` (its picture, optional — migration `20261103090000`) via `PUT /api/pathway-templates/:id/website`. The public list/detail drop pathways switched off; both send `image` (that picture, else the first course cover), the list also `places` (hub towns) for the cards, and the detail `hubs` ("Where it runs" on the website). Website pages (3 Nov 2026): the list has a "My child is [age]" picker (`?age=`, `utils/pathwayAges.js`); a pathway's page shows its stages as a `StageLadder` with the chosen stage's courses in place (`?stage=` / `?age=`), "How enrolling works" and a phone enrol bar (`PathwayEnrolBar`, which lifts the WhatsApp button via `--floating-bottom-offset`). The website's pathway enquiry (`EnrollForm` withHub) then offers only those hubs (else the old hub-type picker) and sends `hubId`, which `LeadService.submitLead` keeps when it's an active hub of `PUBLIC_CONTENT_ADMIN_ID`. Only the website workspace's settings matter.

### Pathways sold by subscription (plans)

`server/src/modules/pathway-subscriptions/` (4 Nov 2026), on the Tech Club pattern. Plans are the ONLY way a pathway is sold online.

**The one-off price is removed** (also 4 Nov 2026). It was Settings → Pathways → Price (whole / per course):
- gone: its API (`PUT /api/pathway-templates/:id/pricing`), `shared/utils/pathway-pricing.js`, the public `price` / course `price`, and the website's one-off displays and "Pay once";
- the `pathway_templates` columns `pricingMode` / `priceAmount` / `coursePrices` are left in the database, unused;
- one-off `invoiceType: "pathway"` invoices issued before then still switch their children on when paid, and give lifetime access (`pathway-enrollment.service.js`'s `activateForPaidInvoice` → `grantPurchasedAccess`).

A pathway is on the website ONLY while it is shown and has a published plan (`public-site.service.js`'s `onWebsite`, plus at least one hub): otherwise it isn't listed, its page 404s and its sign-up is refused — there are no "enquiries only" pathways (4 Nov 2026).

**Plans.** A pathway's plans are in Billing → Packages → Pathway plans (`pathway_packages`, one catalogue pathway each — `pathwayTemplateId`). Each plan has a price per week / month / quarter / year (never daily) for `childrenIncluded`, plus extra children up to `maxChildren`. Billing → Packages → Pathway plans is a package list like Home Learning / Tech Clubs (`PackagesPanel` programme="pathway"): each plan's form picks the pathway (a dropdown of the pathways the curricula use — the directory) and shows that pathway's picture and hubs (`PathwayWebsiteFields`), saved with the plan through `PUT /api/pathway-templates/:id/website` (staff need Billing edit; it also keeps the pathway's shown flag on). Publishing a plan is what lists the pathway; there is no separate show switch. These used to be in Settings → Pathways, which is read only again (a link points to Billing).

**Website.** The public pathway list and detail send `plans` (published) and `subscription` ({ from, billingPeriod }). The website pathway page shows plan cards ("Choose X" → `/enroll?flow=pathway…&plan=<id>`). `PathwayEnrollForm` picks plan + hub (or "Pay once" when there is also a one-off price) and sends `packageId` to the same `POST /api/public/pathway-enrollments`.

**Sign-up.** A plan is required (`packageId`; without one the sign-up is refused). `pathway-enrollment.service.js` makes a `pathway_subscriptions` row (pending) with `pathway_subscription_children` and raises the first period's invoice (`invoiceType: "pathway_subscription"`, `billing_invoices.pathwaySubscriptionId`, billed to the parent). The children's accounts stay ACTIVE: what waits is the pathway's access.

**Access is per pathway, never per account.** `learner_pathway_access` (`pathway-access.js`) covers every stage's courses of the pathway in its curriculum. `course.controller.js`'s `assertCourseAccess` allows a learner their class's curriculum OR `openCourseIds`, so no class is needed (self-paced; a hub class is optional). A subscription's row runs to `accessUntil` = the last paid period's end + the workspace's grace days. A one-off invoice raised before 4 Nov 2026, once paid, gives a row with no end (source "purchase", `grantPurchasedAccess`).

**Billing.** `package-billing.js` has a third kind (`pathway_subscription`), so invoices are raised automatically every period. Paying (`billing.paid-hooks.js` → `PathwaySubscriptionService.activateForPaidInvoice`) makes it active and moves `accessUntil`.

**Lapse and renew.**
- `npm run billing:process` runs `processLapses`: a subscription whose access has run out, with an invoice unpaid past the grace days, is paused. That invoice is cancelled (nobody owes for time without access), billing stops and the courses lock, with progress kept. Accounts are never paused.
- A sign-up never paid within `PATHWAY_UNPAID_RELEASE_DAYS` (default 14) is cancelled.
- Renew (`renew` — parent: `POST /api/pathway-subscriptions/mine/:id/renew`; staff: Switch back on) starts a fresh period today, unless still inside a paid one. It decides from what's paid, not from `billedThrough`.

**Screens.**
- Staff: the Pathway Subscriptions page (`/pathway-subscriptions`, staff module `pathway-subscriptions`; plan edits and invoicing count as billing). It has pause / cancel / switch on, change plan (from the next period) and invoice next period.
- Learner: My Courses lists their pathways (`GET /api/pathway-subscriptions/access` → `PathwayAccessSection`), open or locked, even without a class.
- Parent: the parent home shows their subscriptions with Pay / Renew (`ParentSubscriptions`). The parent's invoice list includes subscription invoices.

Tested end to end on local data (25 checks, `pathway-subs-test.js` in the session scratchpad).

### A child's login password, shown to staff

Learner page → **Login** (`LearnerLoginDialog`): the child's username, their password on **Show** (`GET /api/learners/:id/login-password`, admin/hub/staff with learner access, never a hub lead; every call recorded in Activity via `AuditService.recordViewed`), and setting a new one (`PUT /api/learners/:id` with `learnerPassword`). Passwords stay one-way hashed on `users`; a second, AES-256-GCM-encrypted copy is kept in `learner_login_secrets` for children's username logins ONLY (`auth/learner-password-vault.js`, key `PASSWORD_VAULT_KEY`, else derived from `JWT_SECRET` — changing it makes kept passwords unreadable, never blocks sign-in). Every password write in `auth.service.js` calls `LearnerPasswordVault.remember` (it drops the copy for non-child logins); a child login auto-created at first sign-in from the parent's password keeps nothing. Passwords set before 2 Nov 2026 can't be shown until set again. Never keep a parent's, staff's or admin's password this way.

### Session reports follow each mark (and revoking)

A learner's session report goes out the moment ONE of the session's assessments is marked and released, and is updated as each further one is (`report.service.js`'s `generateSessionReport`; `content.complete` / `content.pendingCount`; the learner's report shows "N more still to be marked"). It's rebuilt straight after marking, auto-marking on hand-in, releasing or revoking (`assessment-submission.service.js`'s `refreshSessionReport` → `ReportService.refreshSessionReportsForAssessment`), not only when a staff page opens. So a session REPORT no longer means a session is DONE: use `sessionDone` (every attached assessment marked, or filed "not submitted") — the course's final report (`isCourseReadyForLearner`), course progress / certificates (`getCourseProgressForLearner`) and claims (`claim.service.js`) do. An educator revokes an issued assessment (teacher Assessments page beside the class's roster, or the roster page — `DELETE /api/assessment-submissions/issues/:id`): it disappears from learners' lists; their work on it is kept but stops counting (`liveGradedSubmissions` ignores submissions whose issue is gone), and their session reports are rebuilt (one left with nothing marked is removed). The teacher's Assessments page groups sessions by module (module picker, module name on each session and in the Issue dialog).

### Reissue and revoke, for chosen learners (5 Nov 2026)

Rules in one place: `assessment-submission.service.js` ("Reissue and revoke: the rules"). Both act on chosen learners of a CLASS issue — a reissue's own id always resolves to its class issue (`rootIssueOf`) — and only on individual assessments (a group assessment is revoked for the whole class, never reissued to one member).
- **Reissue** (`POST /issues/:id/reissue` with `learnerIds`; one `learnerId` still works) → `{ reissued, skipped: [{ name, reason }] }`. A reissue is a new issue for that learner alone (`classId` null, `reissuedFromIssueId` = the attempt it follows). Allowed only when the learner's LATEST attempt is marked (`reissueBlocker`: not before they hand in, not while it waits for marking, not while a reissue waits, never while revoked). The learner gets a bell notice (`assessment_reissued`).
- **Marking a reissue:** it's marked on the class issue's roster (`getRosterForIssue` rows carry `attempts`, `issueId` of the latest, `revokedAt`). Needs Grading tags it (`reissueOf`). Handing it in notifies the class educator (`assessmentSubmitted` resolves the root). Reports count only the latest released attempt per assessment (`buildReportContent`).
- **Revoke for chosen learners** (`POST /issues/:id/revoke-learners`, undone by `/restore-learners` — "Give it back") → an `assessment_revocations` row per (class issue, learner). It covers every attempt (`AssessmentRevocationModel.revokedIssueIds`): off their list and course pages, start / save / hand in / mark refused (`assertNotRevoked`), out of the marking queues and analytics, work kept but not counted (`liveGradedSubmissions`), and no longer required of them (`getLearnerRequiredAssessmentIds`), so their session and course can still finish.
- **Revoke for everyone** (`DELETE /issues/:id`) deletes the class issue, every reissue of it and its revocation rows (work kept). Reissues orphaned by an earlier whole revoke are treated as revoked. It's as if it was never issued: the session still asks for the assessment, so it's issued again or the session filed "not submitted" (its old work no longer makes it "needs grading").
- **Which work counts — one rule** (6 Nov 2026, `assessments/submissions/counted-work.js`), used by reports (session + course, done checks, readiness, not-submitted), competencies (`getLearnerIndicatorProgress[ForAssessments]`) and analytics (time to task, assessments, competencies, at risk): the issue still stands, the chain before a reissue still stands, not revoked for the learner, and per learner per class issue only the LATEST attempt in chain order (never by marking date — re-marking attempt 1 doesn't bring it back); reports only released work. Work counts in the session it was issued for (`forSession`), never in another session attaching the same assessment; not tied to the class, so a learner who changes class keeps it. A new place that counts marked work must use it.
- **Reissue rule** is `reissue.rules.js` (`reissueBlockerFrom`, pure, `test/reissue.test.js`): also refused for a learner no longer in the class. The roster sends it per row (`reissueBlocker`), the client only falls back to its copy. UNIQUE (`reissuedFromIssueId`, `learnerId`) — migration `20261106090000` — so two reissues sent at once make one.

### One login, several roles

`server/src/modules/auth/account-roles.js`. ### Signing in whatever the browser allows

The sign-in is an httpOnly cookie. A browser that won't keep it (cookies / site data blocked, some in-app and privacy browsers) still signs people in, with no message (3 Nov 2026): login and switch-role also return `sessionToken`; `AuthContext.login` checks `/api/auth/me` straight away and, if the cookie was dropped, keeps the token for this tab (`services/fallbackSession.js` — sessionStorage, else the tab's `window.name`, via `utils/safeStorage.js`) and `api.js` sends it as `X-Session-Token` (server: `shared/utils/session-token.js`'s `sessionTokenFrom` — the tab's own header first, then the cookie, then a Bearer header; used by `protect`, switch-role, logout and the rate-limit key). One browser, two people (5 Nov 2026 — a child's tab showed "not linked" after an educator signed in in another tab, since every tab shares the cookie): the sign-in check compares WHO `/me` answers as (`sameAccount`), not just that it answers — a cookie still holding another account's sign-in puts the tab on its own token; every sign-in broadcasts `signed-in` and other tabs showing a different account reopen as it ("/"), plus a check when a tab comes back into view (browsers without tab messages); a tab on its own token is left alone, and its logout / switch-role never clear or set the shared cookie (`usesOwnToken`). Never read `window.localStorage` / `sessionStorage` directly in the portal — a blocked browser throws on the read; go through `utils/safeStorage.js`. A `fetch` outside the axios instance must add `fallbackHeaders()`.

### Deleting something still in use

There are no DB foreign keys, so every delete of something others depend on (curricula, hubs, courses + their modules/sessions, assessments, classes, class groups, educators, learners, competencies, a curriculum's adopted competencies/indicators/pathways/stages/bands, system levels, items, rooms, access roles, bootcamps, games, supervisors, Home Learning + Tech Club packages, QA templates) calls `UsageService.guardDelete(req, res, type, id, "This X")` (`server/src/modules/usage/usage.service.js`) after its own permission checks: in use → 409 `IN_USE` with what uses it; nothing is unlinked. `?check=1` on the same DELETE only answers `{ inUse, usages, alternative }` (no delete, no audit row). Client: each api module has a `check…` twin (`checkDelete` in `services/api.js`); pass it as `ConfirmDialog`'s `usageCheck`, plus `onAlternative` where the record can be deactivated/archived instead. `InUseNotice` (App.jsx) shows any refused delete. A new deletable record type: add it to `CHECKS` + `OWNER`, guard the route, wire the dialog. One exception to "block, never cascade": a developmental stage's OWN parts (each pathway's row for that stage, with its course/assessment tags, and its performance bands) go with it (`CompetencyService.deleteAgeCategory`, 3 Nov 2026 — a duplicated curriculum's stages could never be deleted otherwise); learners placed at it / in its bands / on its pathways, diagnostics issued for it and bootcamps running its pathways still block. A duplicate's stages are its own records, so the original never changes. Rule (3 Nov 2026): a delete inside a curriculum only ever changes that curriculum. A duplicate has its own stages, pathways, bands, levels, types, competency links, indicators, versions and academic years; it shares courses and assessments, which its pages only unlink, never delete. Deleting a whole curriculum keeps any of its assessments a course session uses or that was issued (releasing them from the curriculum) and deletes only its unused ones.

A hub with `deliveryMode` `virtual` or `hybrid` teaches online. Each of its classes can have its own `classes.meetingLink` (Edit class, 2 Nov 2026 — so classes meeting at the same time never share a room); the hub form's `meetingLink` (Google Meet, Zoom…) is the default for classes without one. `TimetableService.resolveCalendar` puts the class's link, else the hub's, on each of its calendar events (`onlineLinkForClass`; client copy `onlineLinkOf(hub, cls)`), so every calendar (educator, learner, parent, hub) carries it — never the public site. Client: `modules/timetable/components/OnlineClass.jsx` — Join on timetable cards and the session pop-up, a "Next online class" card on the educator / learner dashboards, an "Online class" strip on My Courses, each course page, Course Content class cards and My Class, a Join under the parent's "Next session", an Online tag in hub lists; green ("live") from 15 minutes before a session until it ends. Meet opens in a new tab (it can't be embedded). Any web link that opens the meeting is accepted (scheduled or instant Meet, Zoom, Teams…); a Meet link with a code is saved as the plain `https://meet.google.com/abc-defg-hij` (`meetingLinkSchema`, server and client copies). No per-session links; no Google API — meetings are made by hand from a (preferably Workspace) account.

### Enquiry housekeeping

`server/src/modules/leads/lead.housekeeping.js`, run daily by `npm run enquiries:process` (cron, mornings); rules in Settings → Enquiries (owner only; one `enquiry_settings` row for the installation — every admin sees every website enquiry). No enquiry is ever deleted: a daily `enquiries_waiting` reminder (to `PUBLIC_CONTENT_ADMIN_ID`'s admins, else every admin; deduped per day) about enquiries still New after N days; New/Contacted enquiries with no change, reply or note for N days are Closed (`leads.autoClosedAt`, a note on the thread) unless a sign-up, invoice, learner or payment came of them; and, off by default, Closed ones untouched for N months lose their personal details (`leads.anonymisedAt` — name, email, phone, child's name, message, the replies/notes). Website enquiry notifications go to the enquiry's workspace's admins once each (`lead_submitted:<id>` dedupe); personal notifications use `NotificationService.notifyPerson` (never fanned out to an organisation's admins like `_notify`).
